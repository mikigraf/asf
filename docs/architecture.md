# Architecture and durable reactor

## Product boundary

ASF is a single-tenant control plane. A provisioned V1 database has one immutable tenant guard enforced by PostgreSQL; fresh unprovisioned test schemas may remain unbound for isolated fixtures. ASF's product boundary is to decide whether work is ready, record acceptance, compile policy, schedule attempts, sign authority, maintain budgets and approvals, reconcile external truth, independently verify evidence, and close the source item. It does not execute repository code. The current Rust implementation covers the durable core and selected activities; the production dispatch-to-closure path is intentionally incomplete and fail-closed.

Runmill owns one attempt: workspace isolation, implementation, exact-candidate checks, independent review, GitHub delivery, and signed run evidence. ctxlane owns provider profiles, principals, short-lived role leases, and isolated provider state. Coding models own none of acceptance, credential selection, policy, external mutation, or completion.

```text
Linear / authenticated API (untrusted content)
                    |
                    v
          ASF API + deterministic intake
                    |
                    v
        PostgreSQL authoritative ledger
          |         |          |
          |         |          +-- approvals / attention / audit
          |         +------------- jobs / timers / outbox / effects
          +----------------------- work / attempts / signed authority
                    |
             durable reactor activity
                    |
                    v
 local Runmill control -> Runmill controller
                              |
                              v
                       local ctxlane service
                              |
                              v
                    isolated coding identities

object storage <- evidence and artifacts
OTel backend   <- correlated traces, metrics, logs
```

The exact Runmill Work Order, signed-evidence, and private Unix-socket control contracts in this repository have been source-tested against the adjacent Runmill checkout. The control client implements health, submission, run/event/evidence reads, cancellation, and outcome acknowledgement. Complete optional groups let `asf-server all` wire cancellation, health reconciliation, a durable read-only Runmill cursor observer for streams explicitly inserted beneath already-authoritative runs on one configured worker row, GitHub-backed evidence verification, and Linear intake/source closure. Each due stream produces one exact job/checkpoint, reads `get-run` plus one bounded event page after the retained cursor, and atomically commits immutable provenance/result, cursor state, and job completion. A restart can use a new live same-generation observer session without rewriting the immutable session that admitted the run. A compacted event gap retains the exact reads and becomes an owned terminal job escalation; a terminal page parks at `TERMINAL_READY`. An ordinary non-gap observer exhaustion is owned dead work that the next producer pass reconciles: a bounded `SKIP LOCKED` scan records one append-only terminal-failure fact for the exact stream, checkpoint, job, effective escalation, and durable failure digest, then releases the stream to `ESCALATED` at its unchanged cursor in the same transaction. It never fabricates a snapshot or result, never advances the cursor, and never replaces the observer job. None of these outcomes projects into `runs` or `raw_run_events`, because the production reducer/evidence handoff remains absent. The verifier reads signed artifacts through a development-only filesystem store. ctxlane profile/principal readiness and lease attribution, Runmill submission/recovery, authoritative-run stream installation/adoption, event reduction, evidence ingestion/artifact-byte retrieval, and production S3 remain absent. Consequently, new-run dispatch and the full path shown in the diagram remain unavailable.

## PostgreSQL is the system of record

Queue notifications and in-process channels may reduce latency, but neither is authoritative. PostgreSQL holds:

- immutable source snapshots, policy versions, Work Orders, raw run events, and evidence bundles;
- work items, attempts, workers, runs, approvals, escalations, operational incidents and their immutable lifecycle receipts, and accountability anchors;
- workflow instances, jobs, timers, and durable per-run observation streams/checkpoints/results;
- effect intents and an outbox for remote mutations;
- reservations, append-only budget entries, persistent circuit breakers, and audit events;
- artifact metadata and evidence verification results.

The schema enforces important properties at commit time: one active attempt per work item, one authoritative run per attempt, exact work/attempt/Work Order/run/worker coordinates, and raw events bound to the exact run-owned session, worker, and generation. One observation stream per authoritative run has a monotonic cursor/epoch/version, at most one exact job/checkpoint, immutable per-page results, an immutable run-admission session, and a separately live current observer session. Releasing an active checkpoint requires its exact retained result; this intentionally prevents generic observer-job exhaustion from clearing the pointer or advancing the cursor without retained reads. Cursor gaps cannot advance, terminal-ready streams cannot silently reopen, and stale worker generations or sessions cannot write snapshots. The schema also enforces one active repository WIP reservation, immutable signed authority/evidence, effect-request identity, terminal effect/job receipts, and outbox facts; append-only budget/audit data; legal work-item and operational-incident transitions; and a live accountability reference for accepted work. A Runmill submission intent is relationally bound to its immutable Work Order and digest, limited to one logical submission per attempt, and may be `IN_FLIGHT` only while owned by the exact live attempt-bound `ADVANCE_ACCEPTED_WORK_ITEM` job and fence. A valid evidence decision freezes the exact artifact manifest and must retain a strict receipt matching the evidence/run plus the exact completed `VERIFY_EVIDENCE` job, fence, completer, and database-bounded observation/verification chronology. Incident creation and dead-job ownership are reciprocal. Each lifecycle update must commit with an immutable semantic-request receipt whose complete audit/outbox facts and canonical before/after lifecycle digests match the state transition. Multiple exhausted jobs on one attempt adopt one row-locked active escalation without replacing its owner, path, prerequisites, or original SLA; each job retains its own immutable result/audit/outbox snapshot. Reservation transitions require an exact fenced event and one exact RESERVE/RELEASE ledger row per budget reservation. Budget-child validation advances a guarded parent accounting version, forcing a concurrent terminal writer either to observe the child or fail serialization even with a stable transaction snapshot. The reserved `asf-internal:` namespace is additionally bound to the exact expiry transition.

## Cancellation integrity

Synchronous cancellation before dispatch needs a serializable negative fact, not a best-effort scan for rows that happen not to exist. Every work item therefore has one `work_dispatch_fact_guards` row. Migration backfill and triggers treat attempts, non-baseline workflows/jobs, timers, reservations, Work Orders, effects, runs, approvals, evidence, escalations, and budget activity as dispatch facts. The pristine `WORK_ITEM_DELIVERY` workflow and its untouched `ADVANCE_ACCEPTED_WORK_ITEM` job are the only baseline exceptions. The first dispatch fact changes the guard from false to true and advances its generation; it can never return to false. Writers lock the parent work item before changing the guard, closing insert-phantom and erase/rebind races with the pre-dispatch transaction.

The `PRE_DISPATCH` route locks the pristine workflow/job, work item, accountability anchor, and false guard without waiting. It proves the exact accepted-job payload, completed acceptance idempotency record, reproducible acceptance audit hash, and absence of every dispatch fact. The same transaction cancels the advance job and workflow, moves the work item to `CANCELLED`, advances the anchor, writes the cancellation idempotency/audit/outbox facts, and inserts a deterministic immutable terminal receipt containing the exact IDs, versions, fences, before/after digests, and guard generation. Deferred reciprocal triggers prevent later writes from severing that proof, and dispatch-fact triggers reject any attempt to cross the frozen boundary.

Terminal cancellation and verified source closure share a second per-work serialization row, `work_cancellation_authority_guards`, because proving finality must also exclude a concurrent child phantom. Every new guarded work-scoped attempt, run, workflow, job, timer, effect, reservation, approval, escalation, or Work Order crosses this boundary even when the inserted row claims to be terminal; a reactivation or work-binding move crosses it as well. A `CANCELLED` receipt or the exact observed Linear `close_source` effect advances the row once more and freezes one mutually exclusive terminal reference. Both terminal validators prove that no live authority remains. A writer that wins first is therefore visible to or conflicts with finalization, while a writer that loses cannot advance the frozen guard. Existing rows may still make their legal live-to-terminal transitions in the source-closure transaction after the guard freezes. This is a normal PostgreSQL row-version conflict and durable terminal fact, not a commit-time advisory-lock inference. `PRE_DISPATCH`, Runmill `CANCELLED`, and verified `CLOSED` source completion all close the boundary.

Cancellation of an authoritative Runmill run is a different receipt route. ASF first persists one immutable request effect. The request result creates a deterministic append-only `INITIAL` observation bound to the exact workflow-job claim, owner, fence, attempt count, request digest, run coordinates, external generation/state/sequence, reconciliation flag, and database observation time. If the run is not terminal, the job retries or schedules a dedicated observer; each later claim may append exactly one `OBSERVER` that names the prior observation. The chain may grow to arbitrary depth, but every link remains in the same cancellation workflow and preserves the request, disposition, external generation, reconciliation flag, and nondecreasing observation time while enforcing monotonic phase/state/sequence progress. A prior link has at most one successor, and the effect's initial observation cannot be swapped.

Completing a nonterminal `INITIAL` observation creates one deterministic observer obligation. That observer remains available to the ordinary lease, claim, retry, exhaustion, and dead-letter machinery, including its owned escalation path. A separate deferred guard only forbids changing it directly to `CANCELLED` while no immutable terminal receipt cites a terminal `OBSERVER` from the same tenant/work/attempt/run/effect/workflow chain. Administrative cancellation therefore cannot erase the duty to discover remote terminal truth.

If that observer exhausts, a later explicit operator cancellation may recover only the exact current attempt-level `WORKFLOW_JOB_EXHAUSTED` owner. The API locks the shared authority guard, rejects any competing escalation, preserves the complete immutable `DEAD`-job set, terminalizes that one escalation as `CANCELLED`, enqueues a replacement cancellation job, swaps the accountability anchor, and moves the work item back to `CANCEL_REQUESTED`. Trigger-generated escalation, anchor, and work transition facts capture the real OLD/NEW rows. An append-only supersession receipt binds those facts to the idempotency record, request digest, authority generation, replacement workflow/job, audit/outbox facts, and retained evidence. Attempt-less exhaustion and every other escalation category remain outside this recovery route and fail closed.

Only a terminal observation may complete the cancellation workflow. In that transaction ASF releases every active reservation for the exact attempt and authoritative worker using the stable `runmill-cancellation:v1` namespace, records the terminal run/attempt/workflow/work projection, audit event, outbox event, job result, and accountability anchor, then inserts an exact terminal receipt that binds all of those facts to the chain tail. Each released `reservation_sets` row stores that receipt in `cancellation_terminal_receipt_id`; the deferred foreign key requires the receipt to be born in the same commit. A closed check reserves `runmill-cancellation:v1:{work}:{attempt}:{set}:fence:{prior}` for this path and binds it to the exact set coordinate and prior fence, while reciprocal validation binds the release actor and time to the terminal observation and receipt. At the receipt's one-shot deferred commit boundary, the outbox row must still be freshly publishable: `PENDING`, unclaimed, zero-attempt/fence, unpublished, error-free, and available at the database-bound cancellation time. Once that proof commits, the normal publisher may claim, retry, publish, or otherwise advance the outbox delivery lifecycle; the historical receipt does not freeze those mutable transport fields. A nonterminal request or observer never releases attempt capacity. A `CANCELLED` outcome anchors completed cancellation to the receipt and freezes the cancellation-authority generation; any other terminal Runmill phase becomes `TERMINAL_CONFLICT`, retains an owned `REMOTE_EFFECT_AMBIGUOUS` escalation, and leaves the authority guard unfrozen.

`TERMINAL_CONFLICT` is deliberately a historical receipt, not a terminal-authority freeze. Its insert-time proof certifies the exact escalation creation or conservative merge and the matching work, workflow, anchor, audit, outbox, and run projection. It carries no cancellation-authority generation, so the waiting workflow, active escalation, and later legal remediation remain possible. A new escalation's `opened_at` is the terminal observation's database `observed_at`, and its deadline is exactly four hours later. For an existing escalation, the deadline becomes the earlier of its old value and `observed_at + 4h`.

The merge receipt cannot be inserted directly. It is generated only by the escalation-update trigger while the exact terminal cancellation job is still a live unexpired `RUNNING` claim and the authoritative run, effect, initial observation, and terminal observation agree. It binds that job/effect/observation provenance and preserves full OLD and NEW row digests. The trigger admits only the conservative transform: identity, ownership, lifecycle timestamps/status, and idempotency stay fixed; severity cannot decrease; prior semantic text and array evidence/path/prerequisites are retained and augmented deterministically; automatic retry is disabled; active-effect accountability is true; the run is bound; the version advances by one; and the deadline can only move earlier. Later acknowledgement, resolution, cancellation, or other legal escalation lifecycle work remains governed by that lifecycle's own fencing and audit rules and does not rewrite or invalidate either historical receipt.

Reciprocal terminal triggers use a no-finality fast path for ordinary child writes: when neither a committed terminal work state nor its frozen guard reference is visible, they return before taking the parent work lock. This intentionally avoids a child-to-parent lock edge against the runtime's parent-to-child order. Phantom exclusion does not depend on that deferred check or on an advisory lock: every guarded insert or reactivation has already advanced the shared finality row immediately, and cancellation or source closure freezes its winning generation. If a child wins the guard while finalization holds the work row, the child can commit without waiting on that parent; finalization then observes it and rolls back its no-live proof. Once finality is visible, new children fail at the guard before the reciprocal proof needs the parent lock. The shortcut is therefore part of the deadlock strategy, not a relaxation of receipt integrity.

## DB-backed durable reactor

`asf-server all` supervises the HTTP API and an application-level durable reactor over PostgreSQL. The reactor promotes durable timers, produces one bounded observation job for each due explicit stream whose worker route is ready, claims only ready handler types, renews leases, retries with bounded backoff, and reclaims expired claims with higher fence tokens. Reactor leases must exceed the poll interval and have a maximum of exactly 24 hours; configuration, reactor options, and PostgreSQL claim/renew entry points reject any over-limit duration. Every poll also expires a bounded batch of elapsed reservation sets, recording their terminal events and releasing all reserved budget dimensions. Exhaustion of a work-bound job atomically creates an owned escalation; exhaustion of a fully unbound tenant job atomically creates an operational incident reciprocally bound to that exact unbound `DEAD` job. Incident acknowledgement and closure are version-fenced and idempotent, and a valid terminal incident remains the immutable historical ownership record for its dead job after it leaves active attention. Unknown due job types and malformed partial job bindings fail closed.

The following remain the reactor contract for every production activity. Linear intake/source closure, Runmill cancellation/configured-worker health reconciliation, durable Runmill cursor observation, and GitHub-backed evidence verification currently have optional live handlers. Accepted-work advance/dispatch and signed approval remain unclaimable; the Runmill event reducer/evidence handoff and signed-evidence ingestion/artifact retrieval do not have production activities.

1. Commit a state transition and its next job, timer, outbox row, effect intent, audit event, and accountability anchor atomically.
2. Reactors claim due jobs with `FOR UPDATE ... SKIP LOCKED`, an expiring lease, an owner, and a newly incremented fence token.
3. Every side-effecting completion includes the owner and fence token. An expired or superseded claimant cannot commit.
4. Enqueue and external effect requests carry stable idempotency keys. Reuse with different semantics is a conflict.
5. A lost response does not imply failure. The reactor reclaims expired work and reconciles an existing intent/run/effect before retrying.
6. Timers are durable rows, not process-local sleeps. A restart scans overdue timers and jobs.
7. Exhausted jobs become visible dead work and atomically retain an owned work escalation or tenant operational incident; they are never silently discarded. Closing an incident removes active attention but does not erase that historical coverage.
8. Maintenance mode suppresses new dispatch but keeps observation, reconciliation, cancellation, approvals, and evidence access running.

The API derives an opaque activity-capability snapshot from the exact ready handler registry. Its six job-producing operations require `INTAKE_SYNC`, `ADVANCE_ACCEPTED_WORK_ITEM`, `APPLY_SIGNED_APPROVAL_DECISION`, or `VERIFY_EVIDENCE` as an exact ready unscoped type, or require the target worker's exact `RECONCILE_WORKER` or `REQUEST_WORK_ITEM_CANCELLATION` route. Each operation first returns an exact completed idempotency replay, so handler loss cannot invalidate a prior receipt, and applies the capability gate before any aggregate mutation that would create that queue obligation. `ACCEPTED` work with no current attempt is the bounded exception: ASF locks every work-bound job without waiting, proves no dispatch fact exists, cancels the sole advance job, terminalizes its workflow, and records the cancellation synchronously without a worker handler. Once a live authoritative Runmill run exists, cancellation requires that run's exact worker route. The production verifier is registered only when `CLOSE_SOURCE` is ready because a valid verification creates that terminal obligation. After its tenant/core-table checks, `/readyz` groups every live production job by type and persisted activity contract identity, and, for scoped activities, worker route; it fails only for groups outside the installed capability snapshot and remains healthy on an empty unsupported backlog. This preserves health/read/remediation access while preventing new orphan obligations, and does not prove aggregate dependency readiness. This grouping is a process-local capability snapshot, not a durable global reactor capability lease, and no unserviceable-obligation scanner exists yet.

This is at-least-once execution with idempotent/fenced effects, not exactly-once networking. PostgreSQL serialization alone cannot prove whether a remote API performed a mutation after its response was lost; `effect_intents` and provider reconciliation close that gap.

## Recovery model

A process restart does not reset attempts, budgets, WIP reservations, observation cursors, approvals, deadlines, or circuit breakers. The current reactor resumes PostgreSQL job/timer scanning, reclaims expired job leases with a higher fence token, expires elapsed admission reservations, and produces the next page job only from the retained stream cursor. This resumes a retryable active observer claim, and it also reconciles an observer job that reached `DEAD` outside the compacted-gap path. Such a job keeps its owned escalation/accountability; because no completion result exists, recovery consumes an append-only terminal-failure fact instead and releases the stream to `ESCALATED` at the same cursor and epoch. Recovery is crash-safe across the window between the job's dead-letter commit and the stream release, and it needs no live observer session, so a restart repairs the stream before any worker route is ready. It still does not replace the observer job or adopt a run. An observer socket/session restart does not rebind the authoritative run: the stream keeps the immutable admission session while each checkpoint and snapshot prove a current live same-generation observer session. Cancellation persists a stable effect intent before private Runmill I/O. Its identity, idempotency key, correlation marker, request digest, and payload cannot be updated or deleted, and an observed terminal outcome cannot be reopened or rewritten. An `IN_FLIGHT` cancellation records its exact owning workflow-job UUID plus owner/fence; replacement claims cannot impersonate it merely by sharing a reactor owner and per-row fence. Adoption is allowed only after that exact job is no longer a live matching claim. A persisted `INITIAL` observation is reused, while subsequent observation work extends its immutable chain instead of rewriting remote history. If cancellation discovers an already-terminal run, ASF creates or conservatively merges an owned `REMOTE_EFFECT_AMBIGUOUS` escalation, retaining prior evidence and ownership while disabling automatic retries and adding the terminal-conflict prerequisites. Its cancellation receipt remains a creation-time record even when operators later advance the escalation. Worker health is read before database locks; the handler then locks the exact live job and worker, applies a version/generation-fenced projection, appends its hash-linked audit event, and completes the job in one transaction. Unsafe registry/socket/protocol or malformed health facts quarantine the worker and revoke its active sessions. Transient loss marks it offline, and a later healthy probe cannot automatically remove quarantine.

The read-only GitHub observer treats HTTP 429 and GitHub rate-limit or abuse/secondary-limit 403 responses as retryable transport unavailability. Ordinary authorization/policy 403 responses remain provider rejections. Complete GitHub configuration wires this observer into `VERIFY_EVIDENCE` only when the Linear `CLOSE_SOURCE` handler is also ready; the verifier supports only that Linear/pull-request terminal chain and otherwise remains unavailable. When enabled, it independently checks the exact candidate pull request and CI state.

Production recovery still requires capabilities that are not daemon-wired: accepted-item advance/accountability reconciliation, Runmill submission discovery, event-to-workflow reduction/evidence handoff, signed-evidence ingestion, artifact-byte retrieval/S3, and Runmill outcome acknowledgement. The cursor observer retains exact bounded pages and terminal readiness but deliberately does not interpret them into authoritative run/workflow state. The wired verifier and Linear closure handler recover/retry their own durable claims and ambiguous provider result, but they do not create the missing upstream evidence. In particular, Runmill currently reads a run by `run_id` but exposes no lookup by Work Order idempotency key or payload digest. If submission succeeds, its response is lost, and the signed envelope later expires, ASF cannot safely discover or adopt that run. Dispatch remains closed until that contract gap is resolved.

## Contract boundaries

Cross-product contracts are versioned and reject unknown required fields or unsupported versions:

- canonical signed Work Order and Runmill submission receipt;
- Runmill capability negotiation, idempotent submission, snapshot, cursor events, cancellation, and signed evidence;
- ctxlane profile/principal requirements and worker-side readiness result;
- read-only GitHub exact-base-ref/PR observations and Linear effect intents/observed outcomes;
- signed evidence and exact candidate/target expectations.

The Runmill V1 wire contracts have exact Rust fixtures, signature/canonicalization tests, and source checks against the adjacent TypeScript implementation. That is compatibility evidence, not production qualification. The strict Work Order V1 schema also lacks several PRD authority inputs, including a full source reference, risk reasons, planner digest, command policy, and an explicitly named repository-policy digest. A V2 or another immutable referenced contract is required rather than adding fields that Runmill's strict V1 parser would reject.

The configured health handler refuses `READY` unless strict Runmill health is ready, the reported concurrency matches the stored worker, the stored capabilities pass ASF's production-ready predicate, and an active same-generation worker session already exists. It never creates or alters those authority-bearing facts. This is still a health projection, not dispatch admission: Runmill health does not cryptographically prove that the control socket is the exact registered worker key/generation or supply the selected attempt's accepted policy/runtime set and ctxlane profile, principal, environment, and lease evidence. Until those preflights, response-loss discovery, production activity wiring, and external failure-injection tests pass, dispatch is unavailable. In-memory gateways prove algorithms only.

## Data placement

PostgreSQL stores durable state and artifact metadata, not large logs, diffs, or transcripts. Production object storage holds content-addressed bytes with digest, media type, size, producer, encryption class, retention class, and access policy. Workflow rows reference those objects.

Correlation should span:

```text
tenant -> work item -> attempt -> Work Order -> Runmill run
       -> role invocation -> tool/check/effect
```

Large or sensitive artifacts require protected access and retention; they must not be copied into workflow payloads, ordinary logs, or portable evidence.

## Scaling constraints

V1 is one tenant, Linux workers, GitHub/Linear, PR closure, and one active change per repository by default. PostgreSQL job claiming permits several identical ASF reactor processes, but scaling does not relax repository WIP, worker generation, budget, or identity fences. Hosted multi-tenancy, automatic deployment, cross-repository transactions, and unauthenticated remote MCP are outside V1.
